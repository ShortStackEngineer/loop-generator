Verified agent loops

The loop runner that
doesn't believe the agent.

Anything can run a coding agent until the checks go green — your platform probably does it natively. The hard problem is the other one: was the green earned? loop-generator hash-watches the tests and the spec, diffs the workspace for real work, fails runs whose checks were already passing, caps the spend — and hands you a report you can treat as evidence, not as the agent's opinion of itself.

The threat model

Six ways an unattended agent fakes a “done”

Reward hacking isn't hypothetical — frontier coding models have been caught special-casing tests, hard-coding expected values, and editing the very test files that grade them. Most loop runners take the agent's word for it. This one treats every green as a claim to be audited.

It edits the tests

The test files a check runs are the contract. The evaluator-integrity guard hash-watches them across iterations — heuristically detected from the command, plus any explicit guard: paths.

Caught → evaluator-tampered

It rewrites its own success criteria

The .loop.yaml spec is excluded from the work diff and hash-watched when it lives in the workspace. A mid-run edit isn't a clever fix; it's a failed run.

Caught → spec-tampered

The checks were already green

Baseline evaluation runs every check before the agent's first turn. Already passing? Then the checks don't measure the requirement — the loop refuses to launder that into a success.

Caught → baseline-vacuous

“Done” — without changing anything

Every iteration is git-diffed via a throwaway index, with build and runtime artifacts excluded. A green run that changed no source files is flagged as likely vacuous, not celebrated.

Caught → vacuous-success warning

It grinds your budget instead of converging

maxCostUsd and maxTokens cap cumulative driver-reported spend. A satisfied iteration always reports success first — only further spend is refused.

Stopped → budget-exceeded

It crashed, but the checks happened to pass

Drivers report an honest stopReason. An agent that errored or ran out of turns on an otherwise-green run puts a caveat in report.warnings — a warning on a green run is a finding.

Surfaced → warning on the report
And a linter that runs before a single token is spent. loopgen lint catches the misconfigurations that fake results upstream — self-fulfilling smoke tests, wrong workspace, missing binaries, destructive checks — in milliseconds. Every guard and rule, documented →
The deliverable

The report is the product

A run doesn't end with the agent saying “done.” It ends with a LoopReport: a verdict from the outcome list below, every iteration's evaluator results, the diff of real work, and every caveat the guards raised. Green with receipts — or an honest name for why not.

Every way a run can end

success — checks pass, guards quiet
spec-tampered · evaluator-tampered
baseline-vacuous — checks never went red
budget-exceeded · max-iterations
preflight-failed · aborted · error

No outcome is inferred from the agent's self-report. “Done” is a rule over evaluator results — never the model's opinion.

Evidence at three depths

The outcome tells you what happened. Each iteration's evaluator feedback tells you what failed. And observers stream the agent's inner trajectory — turns, tool calls, model output, warnings — as a JSONL trace or standard OTLP spans (zero OpenTelemetry dependency) for Jaeger, Grafana Tempo, or any collector. When you don't trust the verdict, read the trace.

AgentDriver

Agent-agnostic by design

One interface wraps the backend: claude-agent-sdk, grok, github-copilot, opencode, or a scripted mock. One honest scorecard across vendors — the harness auditing the agent isn't sold by the agent's vendor.

Evaluator

Checks that can say no

command covers anything with a CLI and an exit code — tests, linters, type checkers, builds. experiment compares a numeric metric against thresholds or baselines. Or register your own in ~15 lines.

Conformance

Even the drivers are audited

New backend? loopgen verify-driver runs it against a behavioral contract — reports a name, does requested work, applies feedback, handles aborts — before it's trusted inside a loop. Plus .batch.yaml punch lists with dependency ordering and same-workspace serialization.

The spec

The whole contract in one file

Version it, review it, reuse it. loopgen generate -i --verify scaffolds one interactively and proves it's lint-clean and starts RED. 

name: add-retry-to-fetchUser
task:
  type: function
workspace:
  dir: ./target
requirements: |
  Add exponential backoff (max 3 retries) to fetchUser(). Keep the signature.
driver:
  uses: claude-agent-sdk
evaluators:
  - uses: command
    as: tests
    options: { command: npm test }
  - uses: command
    as: typecheck
    options: { command: npx tsc --noEmit }
success:
  type: all-pass
limits:
  maxIterations: 6
  baseline: strict      # fail fast if the checks were already green
  specGuard: error      # editing the spec fails the run
  evaluatorGuard: error # editing the tests fails the run
  maxCostUsd: 5.0
observability:
  observers:
    - uses: otlp           # stream the run as spans to any OTLP collector
      options: { endpoint: http://localhost:4318/v1/traces }

The guards are three lines of YAML. Everything after that is the engine's problem — including proving it to whoever reads the report.

Straight talk

Where this pays off — and where it can't

GOOD FIT  Mechanically checkable work

Overnight and CI runs nobody is watching. A failing test that encodes the new behavior. A metric to move: p95 under X ms, coverage ≥ 90%, bundle under Y KB. Repo-wide remediation against a concrete check. Fleets of agents whose word you'd rather not take.

POOR FIT  Judgment-heavy work

"Improve the architecture." "Make the UI delightful." No exit-zero definition of done means the loop can only tell you the checks were the wrong contract. A passing check doesn't make subjective work good.

And honesty about the guards themselves: they make mis-specified checks, gamed metrics, and context drift visible — they don't eliminate them. If you can't write a check that's RED before the work and GREEN only when the requirement is met, the task isn't ready for a loop. How to prove that up front →

Extending it

Four plug-in points. Zero engine edits.

Drivers, evaluators, task types, and observers are typed registries — register your own and pass them in. The engine, and its guards, never change. 

// a custom evaluator, complete
import { type Evaluator } from "loop-generator";

export const coverage: Evaluator = {
  type: "coverage",
  async evaluate(ctx) {
    const pct = await measure(ctx.workdir);
    return {
      passed: pct >= 0.9,
      score: pct,
      feedback: `coverage ${(pct*100).toFixed(1)}% (need ≥ 90%)`,
    };
  },
};
// a custom observer: ship the evidence anywhere
import { type Observer } from "loop-generator";

export const slackObserver: Observer = {
  name: "slack",
  begin({ runId, spec }) {
    return {
      onRunEnd: (report) =>
        postToSlack(
          `${spec.name}: ${report.outcome} ` +
          `in ${report.iterations.length} iterations`,
        ),
    };
  },
};

Embedding it? The engine is a library too — new LoopEngine(createDefaultRegistries()), with an onAgentEvent callback for streaming the trajectory yourself.
