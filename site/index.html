Feedback loops for coding agents

A prompt gets you one answer. A loop gets you a result — but only if something inside it can say no. loop-generator runs a coding agent against the checks you define, feeds every failure back as the next prompt, and repeats until the checks pass or the budget runs out. With layered guards so a green run actually means something.

How it works

One spec. One engine. Repeat until verified.

A .loop.yaml spec describes the task, the workspace, the agent backend, and the tools that measure success. The engine does the rest.

Each iteration: drive the agent, snapshot and diff the workspace, run the evaluators, check the success criteria, fold the results — including a bounded diff of what the agent changed last turn — into the next prompt.

AgentDriver

Bring any coding agent

One interface wraps the agent backend. Built-ins: claude-agent-sdk, grok, github-copilot, opencode, and a scripted mock for offline runs. A conformance harness (loopgen verify-driver) is the gate for writing your own.

Evaluator

Checks that can say no

The heart of the loop. command covers anything with a CLI and an exit code — tests, linters, type checkers, builds. experiment compares a numeric metric against thresholds or baselines for perf and A/B work. Or register your own in ~15 lines.

TaskType

Prompt scaffolding per category

function, api, webapp, experiment, generic — each frames the agent's instructions and recommends evaluators for its category. Advisory by design: an unknown type falls back gracefully, never breaks a run.

Success criteria

Declarative definition of done

all-pass for the common case; pass, score, and composable all/any/not rules for thresholds and partial gates. Done is a rule over evaluator results — not the agent's opinion.

The differentiator

“All checks passed” — but did they mean anything?

An unattended loop with a weak gate is just an agent agreeing with itself. The engine ships layered false-positive defenses so a green run is a verified claim, not a hopeful one.

Change detection

Every iteration is git-diffed via a throwaway index. A green run that changed no files is flagged as likely vacuous — build artifacts excluded, so merely running the suite can't masquerade as work.

Baseline evaluation

Run the checks before any agent work. Already green? Then they probably don't test the requirement. baseline: strict makes that a hard baseline-vacuous failure.

Spec-integrity guard

The agent can't fake a green by editing its own success criteria. The spec file is hash-watched and excluded from the work diff; specGuard: error fails the run as spec-tampered.

Evaluator-integrity guard

The test files a check runs are the real contract. They're hash-watched too — a mid-run edit surfaces as a warning or an evaluator-tampered failure.

Budget ceilings

maxCostUsd and maxTokens cap cumulative driver-reported spend. A non-converging loop stops with budget-exceeded instead of funding another turn.

Honest outcomes

If the agent errored or ran out of turns while the checks happened to pass, the report says so. Every caveat lands in report.warnings — a warning on a green run is a finding.

Plus a linter that runs in milliseconds. loopgen lint catches the misconfigurations that waste hours — wrong workspace, missing binaries, destructive DB checks, self-fulfilling smoke tests — before a single agent turn is spent. Every rule, documented →
The spec

The whole loop in one file

Version it, review it, reuse it. loopgen generate -i --verify scaffolds one interactively and proves it's lint-clean and starts RED. 

name: add-retry-to-fetchUser
task:
  type: function
workspace:
  dir: ./target
requirements: |
  Add exponential backoff (max 3 retries) to fetchUser(). Keep the signature.
driver:
  uses: claude-agent-sdk
evaluators:
  - uses: command
    as: tests
    options: { command: npm test }
  - uses: command
    as: typecheck
    options: { command: npx tsc --noEmit }
success:
  type: all-pass
limits:
  maxIterations: 6
  baseline: strict      # fail fast if the checks were already green
  evaluatorGuard: error # editing the tests fails the run
  maxCostUsd: 5.0

Straight talk

Where loops pay off — and where they don't

GOOD FIT  Mechanically checkable work

A failing test that encodes the new behavior. A metric to move: p95 under X ms, coverage ≥ 90%, bundle under Y KB. Repo-wide remediation against a concrete check — retries, logging, a lint rule, a flaky suite dragged to green.

POOR FIT  Judgment-heavy work

"Improve the architecture." "Make the UI delightful." No exit-zero definition of done means the loop can only tell you the checks were the wrong contract. A passing check doesn't make subjective work good.

And some things no loop framework can solve: mis-specified checks, agents that game metrics, context drift over long runs. The trust guards make those failure modes visible — they don't eliminate them. If you can't write a check that's RED before the work and GREEN only when the requirement is met, the task isn't ready for a loop. How to prove that up front →

Extending it

Three plug-in points. Zero engine edits.

Drivers, evaluators, and task types are typed registries — register your own and pass them in. The engine never changes. 

// a custom evaluator, complete
import { type Evaluator } from "loop-generator";

export const coverage: Evaluator = {
  type: "coverage",
  async evaluate(ctx) {
    const pct = await measure(ctx.workdir);
    return {
      passed: pct >= 0.9,
      score: pct,
      feedback: `coverage ${(pct*100).toFixed(1)}% (need ≥ 90%)`,
    };
  },
};
// or use the engine as a library
import {
  LoopEngine,
  createDefaultRegistries,
  parseSpec,
} from "loop-generator";

const engine = new LoopEngine(createDefaultRegistries());
const report = await engine.run(
  parseSpec(spec),
  { baseDir: process.cwd() },
);
console.log(report.success, report.reason);

New driver? loop-generator/testing exports a conformance harness that drives it against temp workspaces and asserts the behavioral contract — reports a name, creates files, applies feedback across iterations, handles aborts.
